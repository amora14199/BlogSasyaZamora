1 Pendahuluan

Aplikasi mobile yang memiliki banyak halaman membutuhkan arsitektur navigasi yang rapi agar kode mudah dibaca dan dipelihara. Jika perpindahan halaman ditulis langsung memakai Navigator.push di banyak tempat, kode akan menjadi berantakan (spaghetti code) dan sulit dikelola ketika jumlah layar bertambah.

Pada Praktikum V ini dipelajari dua konsep utama. Pertama, Named Routes, yaitu pemberian nama berupa string untuk setiap halaman yang didaftarkan terpusat di MaterialApp, sehingga perpindahan halaman cukup memanggil Navigator.pushNamed. Kedua, BottomNavigationBar, yaitu menu navigasi di bagian bawah layar yang mengganti tampilan utama (body) tanpa berpindah Scaffold, seperti pada aplikasi modern.

Hasil praktikum ini adalah aplikasi Expense Tracker (pencatat keuangan) yang menggabungkan halaman Beranda (Dashboard), Riwayat, dan Profil dalam satu wadah bertab, ditambah halaman Login.

Pada tahap akhir, seluruh hasil Praktikum 1 sampai 5 digabungkan menjadi satu project. Data pengguna dan data transaksi yang sebelumnya hanya tersimpan di memori kini disimpan secara permanen pada database lokal SQLite, sehingga tidak hilang ketika aplikasi ditutup. Aplikasi juga dilengkapi form register dan login, di mana pengguna dapat mendaftar dan masuk menggunakan akun yang tersimpan di database. Desain UI/UX halaman lain dipertahankan, dan perubahan tampilan hanya dilakukan pada halaman login dan register. Hasil akhir aplikasi dibuat menjadi file APK agar dapat dipasang pada perangkat Android.

2 Tujuan Praktikum

Setelah menyelesaikan praktikum ini, mahasiswa diharapkan mampu:

  • Menerapkan Named Routes untuk navigasi yang terpusat dan rapi.
  • Membangun menu bawah (BottomNavigationBar) seperti aplikasi modern.
  • Mengintegrasikan halaman Dashboard, Riwayat, dan Profil dalam satu wadah.
  • Menyimpan data pengguna dan transaksi secara permanen menggunakan database lokal SQLite.
  • Membuat fitur register dan login dengan data akun yang tersimpan pada database lokal.
  • Menghasilkan file APK sebagai hasil akhir aplikasi.
3 Langkah-Langkah Praktikum
3.1 Alat dan Bahan
  • Flutter SDK
  • Visual Studio Code
  • Emulator / perangkat / browser (Chrome atau Edge)
  • Perangkat Android dan kabel USB (untuk menjalankan dan menguji aplikasi)
  • Git dan GitHub (untuk repository kode sumber)
3.2 Langkah Pengerjaan
1 Mendaftarkan Named Routes

Parameter home pada MaterialApp dihapus, lalu diganti dengan initialRoute dan routes. Rute '/' diarahkan ke MainScreen (layar bertab) dan rute '/add' diarahkan ke AddTransactionScreen.

2 Membuat Penampung Tab

File main_screen.dart dibuat sebagai StatefulWidget karena tab yang aktif selalu berubah. Disiapkan variabel _selectedIndex untuk menyimpan tab aktif, daftar widget _pages yang akan ditukar, dan fungsi _onItemTapped yang memanggil setState.

3 Merangkai BottomNavigationBar

Method build pada MainScreen dilengkapi dengan Scaffold yang body-nya menampilkan _pages[_selectedIndex] dan bottomNavigationBar berisi tiga item: Beranda, Riwayat, dan Profil.

4 Memperbarui dashboard_screen.dart

Pada tombol mengambang (FloatingActionButton), logika Navigator.push(...MaterialPageRoute...) diganti dengan Navigator.pushNamed(context, '/add') agar memakai rute yang sudah didaftarkan di main.dart. Hal yang sama diterapkan pada tombol aksi (Pemasukan, Pengeluaran, Transfer).

5 Hasil Akhir Aplikasi

Aplikasi dijalankan dengan perintah flutter run. Tampilan akhir menunjukkan tiga tab pada menu bawah yang dapat berpindah tanpa mengganti Scaffold, serta tombol Catat Transaksi yang membuka halaman tambah transaksi melalui rute '/add'.

4 Latihan / Tugas
4.1 Halaman Riwayat Transaksi

Halaman riwayat dibuat pada file history_screen.dart. Halaman ini menampilkan seluruh data daftarTransaksi dalam bentuk ListView dan menampilkan pesan khusus bila data kosong. Saat salah satu transaksi ditekan, aplikasi membuka halaman detail transaksi dengan membawa data (passing data).

4.2 Halaman Profil

Halaman profil berisi avatar, nama, email, dan tombol logout. Nama dan email diambil dari class UserSession yang menyimpan data pengguna yang sedang login. Tombol logout mengosongkan data sesi lalu kembali ke halaman login.

4.3 Halaman Login

Halaman login berisi TextField email dan password serta tombol Login. Saat tombol ditekan, aplikasi memvalidasi input, menyimpan email ke UserSession, lalu berpindah ke halaman utama menggunakan Navigator.pushReplacementNamed(context, '/'). Email yang diinput kemudian ditampilkan pada Dashboard dan Profil.

5 Pengembangan Akhir: Integrasi SQLite, Register, dan Login

Pada tahap sebelumnya, data transaksi (list daftarTransaksi) dan data pengguna (class UserSession) hanya tersimpan di memori sehingga hilang saat aplikasi ditutup. Sesuai ketentuan Tugas Praktikum 5, aplikasi dikembangkan dengan penyimpanan lokal SQLite serta form login dan register. Berbeda dengan halaman login pada bagian sebelumnya yang hanya menyimpan email ke UserSession, login pada versi akhir memeriksa data pengguna ke database.

5.1 Menambahkan Package

Empat package ditambahkan pada bagian dependencies di file pubspec.yaml, lalu diunduh dengan perintah flutter pub get. Package sqflite dipakai untuk mengelola database SQLite, path untuk menyusun lokasi berkas database (fungsi join), crypto untuk membuat hash password dengan SHA-256, dan shared_preferences adalah package penyimpanan data sederhana berbentuk key-value.

dependencies: flutter: sdk: flutter cupertino_icons: ^1.0.8 sqflite: ^2.4.5 path: ^1.9.1 shared_preferences: ^2.5.6 crypto: ^3.0.7

Kode 1. Dependencies pada pubspec.yaml

5.2 Membuat Database SQLite (DatabaseHelper)

File database_helper.dart berisi class DatabaseHelper yang dibuat dengan pola singleton (konstruktor privat dan satu instance statis) agar seluruh halaman memakai koneksi database yang sama. Database bernama expense_tracker.db dibuat di lokasi bawaan perangkat (getDatabasesPath) saat pertama kali dibuka melalui onCreate. Terdapat dua tabel. Tabel users berisi id, nama, email (unik), dan password. Tabel transactions berisi id, user_id, title, nominal, kategori, tanggal, dan is_pengeluaran, di mana user_id adalah foreign key ke tabel users sehingga setiap transaksi dimiliki oleh satu pengguna.

5.3 Fitur Register

Password tidak disimpan sebagai teks asli, melainkan diubah menjadi hash SHA-256 melalui fungsi hashPassword. Fungsi registerUser memasukkan data ke tabel users dengan email diubah menjadi huruf kecil. Karena kolom email bersifat UNIQUE, pendaftaran dengan email yang sudah ada menimbulkan DatabaseException dan fungsi mengembalikan false, sedangkan pendaftaran yang berhasil mengembalikan true. Halaman register (register_screen.dart) berisi field Nama, Email, Password, dan Konfirmasi Password, tombol Daftar, serta tautan "Sudah punya akun? Login" (Gambar 22).

5.4 Fitur Login

Fungsi loginUser meng-hash password yang diketik, lalu mencari baris pada tabel users yang email dan password-nya cocok. Jika ditemukan, fungsi mengembalikan data pengguna yang dipakai untuk menampilkan nama dan email pada Dashboard dan Profil. Jika tidak ditemukan, fungsi mengembalikan null dan aplikasi menampilkan pesan "Email atau password salah" (Gambar 24). Halaman login (Gambar 23) memiliki tautan "Belum punya akun? Daftar" yang menuju halaman register.

5.5 Rute pada main.dart

Rute baru ditambahkan pada main.dart. Rute /login menjadi halaman awal melalui initialRoute, /register menuju halaman pendaftaran, / menuju MainScreen dengan BottomNavigationBar, dan /add menuju halaman tambah transaksi. Tema merah dari praktikum sebelumnya dipertahankan.

5.6 Transaksi Tersimpan di SQLite

Penyimpanan transaksi memakai fungsi insertTransaksi, sedangkan pembacaannya memakai getTransaksi yang memfilter data berdasarkan user_id dan mengurutkannya dari yang terbaru (id DESC). Nilai isPengeluaran disimpan sebagai 1 atau 0 karena SQLite tidak memiliki tipe boolean. Karena data ditulis ke berkas database di penyimpanan perangkat, transaksi tidak lagi hilang ketika aplikasi ditutup. Gambar 26 memperlihatkan transaksi "makan malam" sebesar Rp 100.000 pada 25 Oktober 2026 tampil pada Transaksi Terakhir dan saldo utama menjadi -Rp 100.000 karena belum ada pemasukan. Gambar 27 memperlihatkan akun lain yang belum memiliki transaksi sehingga saldonya Rp 0, yang menunjukkan data dipisahkan per pengguna.

5.7 Profil dan Logout

Halaman profil menampilkan avatar, nama, dan email pengguna yang sedang login beserta tombol Logout (Gambar 28).

5.9 Generate File APK

Setelah fitur selesai, aplikasi dibuat dalam mode release dengan perintah berikut yang dijalankan di terminal pada folder project.

flutter build apk --release

Kode 7. Perintah build APK

Proses Gradle (assembleRelease) selesai dalam sekitar 328,9 detik dan menghasilkan file app-release.apk berukuran 48,9 MB pada folder build\app\outputs\flutter-apk. Pesan bahwa font MaterialIcons-Regular.otf di-tree-shake (dari 1.645.184 byte menjadi 4.324 byte) bukan error, melainkan Flutter membuang ikon yang tidak dipakai agar ukuran aplikasi lebih kecil. File APK ini dapat dikirim ke perangkat Android lalu dipasang.

6 Pembahasan
6.1 Named Routes

Dengan Named Routes, seluruh daftar halaman dikumpulkan di satu tempat, yaitu properti routes pada MaterialApp. Setiap halaman dipanggil dengan nama string seperti '/add' atau '/login'. Dibandingkan memakai Navigator.push dengan MaterialPageRoute di setiap tombol, cara ini lebih ringkas, mengurangi pengulangan kode, dan jika nama atau tujuan halaman berubah, cukup diubah di satu tempat. Properti initialRoute menentukan halaman pertama yang dimuat: awalnya '/', lalu diganti '/login' agar pengguna masuk lewat halaman login terlebih dahulu.

6.2 BottomNavigationBar dan State

MainScreen memakai StatefulWidget karena nilai tab aktif (_selectedIndex) berubah saat pengguna menekan menu. Setiap kali setState dipanggil, body pada Scaffold menampilkan widget sesuai _pages[_selectedIndex]. Dengan begitu perpindahan tab tidak membuat Scaffold baru, hanya isi body yang berganti, sehingga terasa seperti aplikasi modern.

6.3 Berbagi Data Antarhalaman

Pada tahap awal, data transaksi disimpan dalam list daftarTransaksi yang dipakai bersama oleh Dashboard dan Riwayat, sedangkan data pengguna disimpan melalui class UserSession dengan variabel static agar email dan nama dari halaman login dapat dibaca oleh Dashboard dan Profil. Keduanya tersimpan di memori sehingga hilang saat aplikasi ditutup. Pada versi akhir, sumber data dipindahkan ke database SQLite agar data tetap tersedia.

6.4 Penyimpanan Lokal dengan SQLite

SQLite adalah database relasional ringan yang tertanam di perangkat dan diakses melalui package sqflite. Seluruh operasi database bersifat asinkron (Future dan await) sehingga tampilan aplikasi tidak terhenti saat data dibaca atau ditulis. Dengan dua tabel yang dihubungkan oleh user_id, data pengguna dan transaksi tersimpan permanen, dan satu instance DatabaseHelper (singleton) dipakai oleh semua halaman sehingga tidak terjadi koneksi ganda.

6.5 Register, Login, dan Keamanan Password

Password diubah menjadi hash SHA-256 sebelum disimpan, sehingga password asli tidak terlihat langsung pada database. Saat login, password yang diketik di-hash lagi lalu dibandingkan dengan hash di database. Email diubah menjadi huruf kecil dan kolom email bersifat UNIQUE sehingga satu email hanya dapat didaftarkan sekali. Sebagai catatan pengembangan, hash tanpa salt masih sederhana; untuk aplikasi nyata sebaiknya dipakai algoritma khusus password seperti bcrypt atau Argon2.

6.6 Data Terpisah per Pengguna

Setiap transaksi menyimpan user_id pemiliknya dan getTransaksi hanya mengambil data dengan user_id yang sedang login. Karena itu akun yang berbeda tidak saling melihat transaksi, seperti terlihat pada perbandingan Gambar 26 dan Gambar 27.

7 Kesimpulan

Berdasarkan praktikum yang telah dilakukan, dapat disimpulkan bahwa penggunaan Named Routes membuat navigasi aplikasi lebih terpusat dan rapi, dan BottomNavigationBar yang dikombinasikan dengan StatefulWidget memungkinkan perpindahan antara halaman Beranda, Riwayat, dan Profil dalam satu Scaffold.

Pada tahap akhir, penyimpanan lokal SQLite berhasil diterapkan sehingga data pengguna dan transaksi tidak lagi hilang saat aplikasi ditutup. Fitur register dan login juga berhasil dibuat dengan password yang disimpan dalam bentuk hash SHA-256, dan data transaksi dipisahkan per pengguna melalui kolom user_id. Seluruh hasil Praktikum 1 sampai 5 telah digabungkan menjadi satu aplikasi Expense Tracker yang berhasil di-build menjadi file APK berukuran 48,9 MB, dengan kode sumber tersimpan pada repository GitHub branch praktikum-5.

Pengembangan selanjutnya dapat berupa penambahan salt pada hash password, fitur ubah atau hapus transaksi, serta pengelolaan sesi login agar pengguna tidak perlu masuk ulang setiap membuka aplikasi.
